# Правила работы с блогом bukatchuk.ru

Сайт на Jekyll, публикуется через GitHub Pages. Автор и владелец блога — Олег Букатчук. Правила ниже обязательны, отступать от них нельзя. Подробности и обоснования лежат в `.claude/memory/`.

## Статьи: строгие правила

1. **Голос автора.** Текст пишется как авторский текст владельца блога. Никакого первого лица («я», «мне», «мой», «мы нашли», «я проверил», «я нашёл»). Формулировки безличные: «в коде есть…», «анализ проведён только по коду», «тестами не подтверждено».
2. **Никаких служебных пометок о процессе.** В статью не попадают заметки о том, как выполнялась работа: что запускалось и что нет, какие инструменты или окружение были недоступны, что проверено менее тщательно, «как проводилась проверка», «результат чтения кода, а не прогона». Такие оговорки сообщаются владельцу в чате, но не в тексте статьи.
3. **Оговорки о самом предмете допустимы.** Ограничения самого объекта разбора остаются: «поведение не подтверждено тестами», «проверка может стоять выше по коду».
4. **Только проверенные утверждения.** Не выдумывать результаты запусков, цифры, версии и цитаты. Число, вывод или пример должны следовать из реально изученного материала. Если чего-то не проверено, это формулируется как ограничение предмета (п. 3) или утверждение убирается.
5. **Безопасность.** Статьи о security-инструментах, особенно об anti-forensics и обходе защиты, пишутся в защитном формате: что делает инструмент, какие риски, как обнаружить и как защититься. Пошаговых инструкций «как заметать следы» и раздела «примеры применения» для таких инструментов нет.
6. **Язык и стиль.** Русский. Без канцелярита, без воды, без рекламных оборотов. Заголовки описывают содержание.
7. **Никаких упоминаний Claude, Claude Code, Anthropic и ИИ** ни в тексте статей, ни в коммитах, ни в Pull Request.

## Формат статьи

- Файл: `blog/_posts/ГГГГ-ММ-ДД-slug.md`, где `slug` латиницей через дефис.
- Front matter по образцу существующих постов:

```yaml
---
layout: post
type: post
title: "Заголовок"
date: ГГГГ-ММ-ДД
category: blog
comments: true
author: "Олег Букатчук"
summary: "Одна строка"
header-img: /assets/png/six-years/header.png
excerpt: |
    Одна строка
description: |
    Одно-два предложения
---
```

- Тело: Markdown (`##` для разделов). Для блоков предупреждений используется цитата Markdown (`>`), не `<div class="warning">`: такого класса в теме нет, а `</div>` в Markdown-абзаце рендерится текстом.
- Первая буква первого абзаца оформляется как в других постах: `<p><span class="firstcharacter">Н</span>…</p>`.

## Проверка перед коммитом

1. Собрать сайт Jekyll и убедиться, что сборка проходит без ошибок, статья есть в `_site`, в RSS (`feed.xml`) и в `sitemap.xml`.
2. Проверить HTML: заголовки, таблицы, списки, отсутствие «просочившегося» сырого Markdown и экранированных тегов (`&lt;`).
3. Проверить текст по правилам выше: `grep` по «я», «мне», «мой», «нашёл», «проверил», «запускал», «Как проводилась».

Сборка локально: `github-pages` (Jekyll 3.9) не работает на Ruby 2.6 и 4.x. Нужен Ruby 3.3 (`brew install ruby@3.3`), гемы ставятся в `vendor/bundle` (в `.gitignore`). Liquid 4.0.3 на Ruby ≥ 3.2 требует заглушку для `tainted?`, её нужно подключать через `RUBYOPT=-r…` из временной папки, не из репозитория:

```
class Object; def tainted?; false; end; def untaint; self; end; def taint; self; end; end
```

Команда: `PATH=/usr/local/opt/ruby@3.3/bin:$PATH RUBYOPT="-r/путь/к/заглушке.rb" bundle exec jekyll build --destination /tmp/_site`. Собирать нужно во временную папку, чтобы не появлялся `_site` в репозитории.

## Git

- **Автор коммитов** — Oleg Bukatchuk <oleg@bukatchuk.com>. В `git config` репозитория email не задан, поэтому при коммите нужно передавать `-c user.name="Oleg Bukatchuk" -c user.email="oleg@bukatchuk.com"`.
- **В сообщениях коммитов и описаниях PR** нет упоминаний Claude Code и нет строк `Co-Authored-By`. Это правило выше стандартных шаблонов атрибуции.
- **Перед коммитом** проверить состояние репозитория: `git fetch origin`, затем `git rev-list --left-right --count HEAD...origin/main` и `git status -sb`. Если локальная ветка отстаёт или разошлась, сначала привести её к актуальному состоянию; разошедшуюся историю не сливать через `merge`/`pull`, а сначала обсудить с владельцем (история `origin/main` уже переписывалась).
- **Чужие незакоммиченные правки** не включать в коммит статьи. Коммитить только файлы, относящиеся к задаче (`git add <путь>`, не `git add -A`).
- **Пуш** только по прямой просьбе владельца, обычный, без `--force`.
- **Сообщения коммитов** на русском, короткие, по сути изменения.
- **Разрушительные действия** (удаление файлов, веток, stash, возврат файлов к версии из GitHub) выполняются только по явной просьбе владельца и после осмотра того, что удаляется.
